## 并发抢车

在真实 MySQL 8.0.46 上准备 20 个独立买家。各会话预先完成登录和 CSRF，再同时请求同一辆在售车辆。结果为 **1 个 201、19 个 409**。数据库中该车有 **1 笔订单、1 条车锁**，按车源编号和订单编号能匹配该待付款订单。

## 分页负载

向独立库插入 10,000 条构造车源。预热 20 次后分 5 轮测试，每轮发出 100 个并发 HTTP 请求，轮流访问每页 12 条的第 1 至 5 页。每个样本计入发起请求到响应 JSON 读取完成的时间，包含网络和应用排队。按 nearest-rank 计算分位数。两种场景均核对返回页码、每页条数和总记录数。

| 请求 | 样本 | 匹配总量 | P50 | P95 | P99 | 错误 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 市场列表 | 250 | 10002 | 527.49 ms | 1081.19 ms | 1297.66 ms | 0 |
| 品牌、城市、价格、年份、里程及交易方式联合筛选 | 250 | 674 | 459.86 ms | 1096.32 ms | 1241.31 ms | 0 |
| 合计 | 500 | — | 499.50 ms | **1088.95 ms** | 1278.13 ms | 0 |

两类场景及合计 P95 均满足 2 秒验收目标。本轮最大时延为 1335.64 ms。对同等过滤与排序的关键分页查询执行 `EXPLAIN`，市场列表使用 `idx_vehicle_listing` 倒序扫描。联合筛选采用 `city_id,brand_id` 的索引合并，随后排序。结果反映本机回环环境本轮数据规模和请求组合。

## 备份恢复

停止验收应用写入后，导出 MySQL 并复制上传附件。把 1,946,962 字节的 SQL 恢复到另一空库。16 张表的行数与源库数据相符，全部 16 张表的 MySQL 扩展校验和一致。复核了车辆锁、代销委托、贷款、售后订单与报告附件关联。8 个附件副本通过 SHA-256 检查。

使用恢复库和复制后的上传目录启动新的应用，实际读取了在售样本和它的封面，HTTP 返回的 316,934 字节与原样图完全一致。

[恢复行数、关联数量和应用读取结果](evidence/recovery.json)
